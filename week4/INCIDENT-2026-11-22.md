# INCIDENT 2026-11-22 · 一条 999°C

> 演练目的：看见**同一条坏数据在三层里不同的命运**——第一层它根本进不去，第二层它被拦在写库前，第三层它进去了但立刻被发现。
> 三层都演过，才知道"为什么不能只留一层"。数据不留在库里，只留证据（`ops.check_result` + 本文）。

## 三层各挡什么

| 层 | 例子 | 挡住了什么 | 挡不住什么 |
|---|---|---|---|
| **外键**（`dim_date` / `dim_city`） | `insert ... values ('wuhan','2027-01-01',...)` → `violates foreign key constraint "fact_weather_daily_date_key_fkey"`，`DETAIL: Key (date_key)=(2027-01-01) is not present in table "dim_date"` | **结构性错误**：日期不在日历维、城市不在城市维。一条都进不去（不是部分成功） | 值本身荒谬（999 是合法 `numeric`） |
| **pre**（8 条，写库前） | `温度值域 [-50, 60] FAIL min=-5.4 max=999.0` → 不写库，exit 1 | **语义错误**：类型合法、业务荒谬的值 | 已经落库的旧坏数据；也看不到历史（行数突变） |
| **post**（6 条，写库后） | `值域（库内越界行数）越界 1 行` → exit 1 + `v_open_alerts` | **已经发生的腐化**；以及"今天没跑"（新鲜度） | 拦不住写入（那时数据已在库里） |

## 为什么 999 能骗过数据库

```text
numeric(4,1) 上限 = 999.9  →  999.0 合法，入库不报错（实测 999.95 才 overflow）
CHECK 只有 tmax >= tmin、非负、precip_h 0–24  →  999 ≥ 5 成立，5 条 CHECK 全过
```

**约束管的是"类型与关系"，不是"业务合理性"。** 所以"值域"这两条（pre 一条、post 一条）必须自己写。

## 修复：重放，不 DELETE

```powershell
Copy-Item week3\data\raw\wuhan.bak.json week3\data\raw\wuhan_2026-11-15_2026-11-21.json -Force
python week4\run_daily.py --start 2026-11-15 --end 2026-11-21 --reuse-raw
```

为什么不是 `DELETE FROM ... WHERE tmax_c > 60`：

- 删完那天就缺了，覆盖率会红，还得再跑一次补回来；
- 重放一步同时完成"删坏值 + 写回真值"，而且**它证明修的是数据源，不是数据库**；
- 这就是 upsert 存在的意义——它让"修数据"变成一个可以反复执行的动作。
